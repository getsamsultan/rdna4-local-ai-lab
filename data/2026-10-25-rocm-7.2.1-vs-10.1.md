# 2026-10-25 — ROCm 7.2.1 vs ROCm 10.1.0, same llama.cpp build

**Question:** with the inference engine held constant, does moving from ROCm 7.2 to ROCm 10.1 change speed on RDNA4?

**Images:** both built from llama.cpp commit `c7fc50941` (build 11804) with its own `.devops/rocm.Dockerfile`, target `full`, `ROCM_DOCKER_ARCH=gfx1201`. Only the base image differs:

| Image | Base | ROCm inside |
|---|---|---|
| `lab-llama:b11804-rocm7.2.1` | `rocm/dev-ubuntu-24.04:7.2.1-complete` | `/opt/rocm/.info/version` = 7.2.1 |
| `lab-llama:b11804-rocm10.1.0` | `rocm/dev-ubuntu-24.04:10.1.0-full` | `/opt/rocm/core-10.1/.info/version` = 10.1.0 (HIP 7.16.26385) |

ROCm 10 images use the new tag suffix `-full` (7.x used `-complete`) and keep the version file under `core-10.1/`. All three R9700s enumerated under ROCm 10.1 with the host's stock kernel 7.0 driver.

**Model:** Qwen3-Coder-Next-UD-Q6_K.gguf · **GPUs:** 0,1,2 · **Flags:** `-ngl 99 -sm layer -fa 1 -ub 256 -p 512 -n 2048 -r 5` · host monitoring agent restarted just before (see the engine-upgrade notes).

## Results (tokens/s, mean ± sd, n = 5)

| Order | ROCm | pp512 | tg2048 |
|---|---|---|---|
| 1 | 7.2.1 | 2414.40 ± 10.22 | 65.35 ± 0.01 |
| 2 | **10.1.0** | **2413.75 ± 9.90** | **65.74 ± 0.02** |
| 3 | 7.2.1 | 2352.96 ± 5.52 | 65.07 ± 0.05 |

**No measurable difference.** Generation +0.8% on 10.1, against a 0.4% spread between the two 7.2.1 runs; prompt reading identical. The third run's lower pp512 (−2.5%) looks like heat after ~15 minutes of load, which is what the repeated A is for.

**Takeaway:** for llama.cpp on gfx1201, the engine version mattered (~+20%, see below); the ROCm version, 7.2 → 10.1, didn't.

## Side result: the engine gain, like for like

With the monitoring agent freshly restarted for both: old image (llama.cpp b8763, ROCm 7.2.0) **54.31–54.47**; this build-11804 image on ROCm 7.2.1 **65.07–65.35**. That's **~+20%**, consistent with the +19% same-session A–B–A, so the "+13%" lower bound in the engine-upgrade notes no longer applies. (The images also differ in build settings: the old one was a patched build from the previous stack, this one a gfx1201-only build of the official Dockerfile.)

## Qwen3.8-Flash-Next 177B (GPUs 0,1), first attempt: inconclusive

`-ngl 99 -sm layer -fa 1 -ub 256 -p 512 -n 2048 -r 3`, agent restarted first.

| Order | ROCm | pp512 | tg2048 |
|---|---|---|---|
| 1 | 7.2.1 | 1158.43 ± 29.12 | 36.68 ± 0.05 |
| 2 | 10.1.0 | 1387.41 ± 3.51 | 36.36 ± 0.03 |
| 3 | 7.2.1 | 1447.62 ± 1.74 | 37.43 ± 0.01 |

The two 7.2.1 runs disagree by 25% on prompt reading and 2% on generation, so this A–B–A doesn't support a conclusion. Likely cause: a cold page cache. This model keeps a 27 GB n-gram embedding table in system RAM, memory-mapped from the file, so the first run paged it in from disk. ROCm 10.1's generation is 1–3% below the 7.2.1 runs, within that drift. Re-test planned: one discarded warm-up run, then A–B–A–B.

## Qwen3.8-Flash-Next 177B, re-test: ROCm 10.1 is slower

Same flags. One discarded warm-up run (so the n-gram table is in the page cache), then A–B–A–B.

| Order | ROCm | pp512 | tg2048 |
|---|---|---|---|
| 1 | 7.2.1 | 1455.19 ± 1.96 | 37.38 ± 0.01 |
| 2 | 10.1.0 | 1396.37 ± 2.34 | 36.40 ± 0.02 |
| 3 | 7.2.1 | 1443.50 ± 0.30 | 37.47 ± 0.02 |
| 4 | 10.1.0 | 1390.22 ± 11.49 | 36.42 ± 0.03 |

Each pair agrees within 1% (generation within 0.25%). **ROCm 10.1.0 is −2.7% on generation (36.41 vs 37.43) and −3.9% on prompt reading (1,393 vs 1,449)** on this model, about ten times the within-pair spread.

## Conclusion

| Model | ROCm 10.1 vs 7.2.1, same llama.cpp build 11804 |
|---|---|
| Qwen3-Coder-Next 80B (qwen3next) | No measurable difference |
| Qwen3.8-Flash-Next 177B (qwen4exp) | −2.7% generation, −3.9% prompt reading |

For llama.cpp on gfx1201, ROCm 10.1 works out of the box with the stock kernel 7.0 driver but isn't faster, and on the newer architecture it's slightly slower. Staying on 7.2.1 for serving; re-test when llama.cpp releases builds tuned for ROCm 10. Lesson: warm the page cache before benchmarking models with large memory-mapped tables, and use A–B–A–B when the first A looks unstable.
